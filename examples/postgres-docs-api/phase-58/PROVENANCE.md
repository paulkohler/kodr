# Provenance

This example was generated by Kodr against the local `qwen/qwen3.6-35b-a3b`
model from this directory.

## Seed Files

- `AGENTS.md`
- `prompt.md`
- initial `README.md`

## Generation

```sh
/Users/paul/src/koder-by-codex/kodr run \
  --prompt-file prompt.md \
  --yes \
  --out .kodr-run \
  --inspect-context \
  --max-turns 8 \
  --max-retries 7
```

Result: Kodr generated and applied a 15-file Express/Postgres API proposal.
Artifacts are in `.kodr-run`.

## Driver Setup

```sh
npm install
docker compose up -d
npm test
```

`npm install` succeeded and produced `package-lock.json`.

`docker compose up -d` could not run because the local Docker daemon was not
available in this session.

`npm test` exposed a generated-code failure before database availability became
the main blocker: generated test helpers named `fetch` recursively called
themselves instead of `globalThis.fetch`, causing stack overflow and out-of-memory
failures.

## Repair Attempts

Kodr repair attempts were made instead of hand-editing the generated solution:

- `.kodr-repair-1`: produced an OK envelope with zero files and a scratchpad
  plan.
- `.kodr-repair-2`: tool-mode repair exhausted the turn budget before producing
  a response.
- `.kodr-repair-3`: narrower repair prompt still produced zero file changes and
  only a scratchpad plan.
- `.kodr-repair-4`: higher-budget tool-mode repair exhausted the turn budget.

The generated app is intentionally left as Kodr produced it. The failures are
learning artifacts for improving repair loops, dependency/service setup, and
proposal validation.
