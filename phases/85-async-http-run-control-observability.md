# Phase 85: Async HTTP Run Control And Observability

## Goal

Promote `kodr serve` from a synchronous channel sketch into an inspectable local
HTTP control plane for driving Kodr runs, observing long local-model work, and
supporting a future web UI without adding a separate execution path.

The HTTP API must remain a thin adapter over the central channel/request layer.
CLI, TUI, and HTTP should share run/session semantics, artifact layout,
progress events, permission decisions, and defaults.

## Context

Phase 50 proved that a zero-dependency HTTP channel can expose sessions and a
simple `POST /turn`. That route waits for the whole model run to finish and
suppresses progress, which makes it awkward for local models that can spend
minutes processing prompts or generating tokens.

For testing and a future browser UI, Kodr needs task-style run control:

- submit a turn and immediately receive a run handle
- inspect whether a run is queued, running, failed, blocked, or complete
- stream progress events while the model, subagents, tools, hooks, installers,
  sandboxes, and tests are working
- retrieve artifacts and session data through safe, bounded HTTP routes
- continue a session with another prompt from the same API

This is inspired by task-oriented sandbox APIs, but Kodr's implementation should
stay local-first, dependency-free, and artifact-backed.

## User Surface

Keep the command:

```sh
kodr serve
kodr serve --host 127.0.0.1 --port 8787
```

Add asynchronous run routes:

```text
GET  /health
GET  /status

POST /runs
GET  /runs
GET  /runs/:id
GET  /runs/:id/events
GET  /runs/:id/logs
GET  /runs/:id/artifacts
GET  /runs/:id/artifacts/:name
POST /runs/:id/cancel

GET  /sessions
GET  /sessions/:id
POST /sessions/:id/turns
```

Keep existing routes compatible:

- `GET /sessions`
- `GET /sessions/:id`
- `POST /turn`

`POST /turn` can remain as a compatibility wrapper around `POST /runs` plus
wait-for-completion, or it can return the same synchronous shape it does today.
New clients should use `/runs`.

## Run Submission

`POST /runs` accepts a bounded JSON object:

```json
{
  "prompt": "Add tests for slugify",
  "sessionId": "optional-session",
  "continue": false,
  "tools": true,
  "yes": false,
  "model": "lmstudio/nvidia/nemotron-3-nano-omni",
  "test": "npm test",
  "install": false,
  "subagentStages": false
}
```

Response:

```json
{
  "runId": "2026-06-05T10-20-30.000Z",
  "status": "queued",
  "sessionId": "",
  "eventsUrl": "/runs/2026-06-05T10-20-30.000Z/events",
  "statusUrl": "/runs/2026-06-05T10-20-30.000Z"
}
```

HTTP turns stay dry-run by default. The client must explicitly pass
`"yes": true` to apply writes. The API must not expose arbitrary raw CLI
options. Each accepted field should map to a typed, validated option already
supported by the shared channel layer.

## Run Registry

Add an in-memory run registry owned by the server process:

```js
{
  runId,
  requestId,
  sessionId,
  status: 'queued' | 'running' | 'blocked' | 'completed' | 'failed' | 'cancelled',
  phase: 'model' | 'planner' | 'implementer' | 'reviewer' | 'install' | 'test' | 'hook' | '',
  model,
  promptPreview,
  startedAt,
  updatedAt,
  finishedAt,
  runDir,
  ok,
  exitReason,
  usage,
  cost,
  lastEvent
}
```

The registry is not the durable source of truth. Completed run details still
come from artifacts under `.kodr/runs` or an explicit `--out` directory.
Restarting `kodr serve` may lose in-memory active-run state, but completed
sessions remain discoverable through existing session browsing.

## Events

Use Server-Sent Events for `GET /runs/:id/events`.

Events are emitted from the same `options.onProgress` mechanism used by CLI and
TUI. The server should keep a bounded replay buffer per run so a client can
connect late and still see recent events.

Event examples:

```text
event: progress
data: {"event":"agent_start","agent":"standard","model":"qwen/qwen3.6-35b-a3b"}

event: progress
data: {"event":"subagent_finish","agent":"planner","responseChars":2434}

event: status
data: {"status":"running","phase":"test"}

event: done
data: {"status":"completed","ok":true,"runDir":".kodr/runs/..."}
```

The event contract should be presentation-neutral. A web UI can render these as
timelines, while CLI tests can assert on plain JSON payloads.

## Logs And Artifacts

`GET /runs/:id/logs` returns structured log/event records, not arbitrary
terminal files. It can include:

- progress events
- channel lifecycle events
- stderr info lines generated by the run adapter
- final summary text

`GET /runs/:id/artifacts` returns a safe list of known artifacts:

```json
{
  "artifacts": [
    "summary.json",
    "conversation.json",
    "response.md",
    "writes.json",
    "tests.json",
    "openshell.json"
  ]
}
```

`GET /runs/:id/artifacts/:name` must only serve files from the known run
artifact directory and must reject path traversal, nested arbitrary paths, and
unknown names unless explicitly allowlisted.

## Multi-Turn API Validation Scenario

The API should be easy to drive from a script:

1. `POST /runs` with `"prompt": "Create src/math.mjs with add()"`.
2. Connect to `/runs/:id/events` and wait for `done`.
3. `GET /runs/:id` and assert `status === "completed"`.
4. Read `summary.json` and capture the returned `sessionId`.
5. `POST /sessions/:id/turns` with `"prompt": "Add subtract() and tests"`.
6. Stream events for the second run.
7. `GET /sessions/:id` and assert both user turns are present.
8. `GET /runs/:secondId/artifacts/tests.json` and assert verification status.

This validates that the HTTP API can drive the same iterative workflow as the
TUI without depending on terminal output.

## Web UI Validation Scenario

A future web UI should be able to consume the API without private hooks:

1. On load, call `GET /status` for server state and active run count.
2. Call `GET /sessions` to populate a session sidebar.
3. When the user sends a prompt, call `POST /runs`.
4. Open `GET /runs/:id/events` and render:
   - current stage
   - subagent start/finish rows
   - tool/install/test progress
   - final apply/test result
5. Poll or subscribe to `GET /runs/:id` for status recovery if the SSE
   connection drops.
6. Call `GET /runs/:id/artifacts` to populate an artifact inspector.
7. Call `GET /sessions/:id` to refresh the transcript after completion.

This forces the API to be inspectable while a local model call is in progress,
not only after artifacts exist.

## Cancellation

Add `POST /runs/:id/cancel` as a first-class route, but keep the first
implementation honest:

- If cancellation is not wired through all blocking operations yet, mark it as
  best-effort and artifact that the request was made.
- The follow-up implementation should pass an `AbortSignal` through model
  requests, tool loops, command runners, installers, verification, Docker, and
  OpenShell where supported.
- Never kill unrelated host processes by pattern.

## Security

The server remains loopback-only by default. Non-loopback binding should require
a separate future phase with authentication.

Rules:

- No dependencies.
- No static frontend bundle in this phase.
- No arbitrary file serving.
- No arbitrary command route.
- No remote host binding.
- No exposing environment variables or provider keys.
- Keep HTTP apply mode dry-run by default.
- Validate every JSON field and reject unknown high-risk options.
- Add a small active-run concurrency limit, defaulting to one run at a time.
- Record enough status to explain when a run is queued because another run is
  active.

## Implementation Plan

1. Add a `RunRegistry` module for active run records, bounded event buffers,
   lifecycle transitions, and lookup by run id.
2. Extend `startKodrServer()` with asynchronous routes while keeping existing
   `/turn` compatibility.
3. Route submitted runs through `handleChannelRequest({ kind: 'run-turn' })`
   with an injected `onProgress` callback that updates the registry and event
   stream.
4. Add SSE support using Node's built-in HTTP response streaming.
5. Add safe artifact listing and retrieval for known run artifacts.
6. Add `/status` and `/health` for server inspection.
7. Add best-effort cancellation plumbing and artifacted cancellation requests.
8. Add tests for route validation, queued/running/completed state, event replay,
   session continuation, artifact jail behavior, and cancellation status.
9. Update `usage.md` with script and web UI examples.
10. Record decisions/failures and write the blog post.

## Non-Goals

- No browser UI implementation.
- No WebSocket dependency.
- No remote multi-user server.
- No persistent server database.
- No authentication scheme in the first pass.
- No arbitrary artifact filesystem browser.
- No direct model-provider proxy route.
- No replacement for CLI or TUI.

## Open Questions

- Should `/runs/:id/events` support `Last-Event-ID` replay semantics from the
  first version?
- Should active run state be periodically snapshotted to `.kodr/server-state`
  for recovery after a server restart?
- How should pending apply-review decisions from the TUI map onto HTTP routes?
- Should permission prompts use the same event stream, or a separate
  `/runs/:id/decisions/:decisionId` route?
- Should cancellation be blocked when safe writes are in the middle of an
  atomic apply?
